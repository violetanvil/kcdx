# Why `add-db-entity` exists

## The function-kind baseline prerequisite (the post-launch upgrade)

The first version checked only that the backend's `/health` reported `state: resolved` — which proves the CURATED DB + the three CSVs are present, but says NOTHING about whether the bulk baseline (`reference-dev.sqlite`) covers a function's RVA. A `function`-kind row's survival datum is a body fingerprint PROMOTED from a matching bulk row, and the validator refuses to mint a function row at an RVA the bulk baseline does not cover (no NULL-fingerprint ghost function). The skill had no guidance for this real prerequisite, so on the first live use the agent hit a `/confirm` baseline rejection it did not anticipate and **invented a wrong explanation**: that the bulk source was "not in the checkout," "may need `git lfs pull`," and "a rebuild may not even be runnable here" — then surfaced it as a dead-end "your call." Every part of that theory was false: the full DB (incl. the bulk baseline) is REBUILT FROM IN-REPO DATA via `import_to_sqlite.py` (the local gitignored Ghidra dump, or the D38 CSV-genesis from `data/db-export[-bulk]/`), the dump dir was present locally, and both DBs were already built. The defect was a `results-driven` violation — theorizing a checkable fact instead of probing it.

The upgrade closes it on the user's two settled choices: (1) a §1 PRE-CHECK before preview — for a function-kind add, query `reference-dev.sqlite` for the RVA's fingerprint (ground truth, not theory); present → proceed; absent → surface the in-repo rebuild as a user-owned op (the agent never runs the multi-hour rebuild unilaterally — `agent-builds-and-deploys` + `design-authority`); plus a §3 reactive guard for any baseline rejection that slips through. (2) The framing is corrected explicitly — the body now STATES the rebuild is in-repo and FORBIDS the exact wrong-theory the agent produced ("unfetchable LFS artifact" / "`git lfs pull`" / "not runnable here"), with a matching Hard rule + anti-pattern. The pre-check also catches the already-curated case (a function whose RVA already carries a non-NULL `kcdx_id` is an UPDATE, not an add → route to the GUI), which the original could not distinguish from a fresh add.

## The gap it closes

`/research-disassembly` §6 ("Handoff — verifying ≠ recording") explicitly names a seam: that skill VERIFIES a game-function fact and produces the provenance, but recording it into the reference DB is "a separate edit — the working flow (`/execute`, or the caller that requested the research) authors the fact into the reference DB via the maintainer tool." The generic answer was `/execute`, which has no per-kind knowledge of what an Address Library row requires and no built-in AP18 approval gate. The maintainer-tool GUI is the human path; there was no AGENT path — a skill an agent mid-`/execute` or mid-research could invoke to record a verified fact through the validated write path, with the per-addition approval AP18 mandates. This skill fills that named seam for the agent.

## Why it drives the backend API, not a direct write (the user's fork 1 choice)

The user chose "drive the existing backend API." The maintainer-tool backend already encodes the entire validated write path: `/save/*` previews (validate through the data-core's single gate, write nothing) → `/confirm/*` transacts (atomic write → CSV export → integrity check → git commit + push, with robust rollback so on any failure nothing lands). The GUI drives exactly this. A skill driving the same API inherits the single validator, the atomic rollback, and the git commit for free — it adds ZERO validation logic, so there is no second copy of the rules to drift (the failure `authoring-process-economy` / the no-monolith family forbid). The rejected alternative (write CSV/DB directly via the data-core) re-encodes the `routes_confirm` orchestration (tag-resolve, rollback, export, git) — a divergent writer that could skip a check the routes enforce, a Capability/UX risk for no cornerstone gain. The "server not required" upside of the direct path is moot: the agent runs the server anyway (`agent-builds-and-deploys.md`).

## Why new-rows-only (the user's fork 2 choice)

The user scoped it to `create-entity` + `create-version` — the two AP18-gated ADDITIONS. These are exactly "adding things to the DB" and exactly what the user's per-approval requirement governs. The rejected "all six shapes" alternative would have the skill duplicate the GUI for four UPDATE jobs (re-verify / supersede / deprecate / edit-notes) that mutate already-approved entities — not additions, not AP18-gated, and well-handled by the GUI. A tight one-job skill beats a broad one that splits the authoring surface; broader capability that isn't asked for is scope creep, not a Capability cornerstone win.

## Why it cites policy.md instead of embedding the rules (the user's fork 3 choice)

The user chose "cite policy.md + require verified evidence; the validator is the gate." The per-row/per-column rules live authoritatively in three places already: `policy.md` (required columns, the audit trio both-or-neither, kind enum, survival columns per kind, supersession/deprecation pair-integrity, FK closure), `schema.py` (the `ADDRESS_KINDS` / `EVIDENCE_KIND_ENUM` / `FUNCTION_KINDS` / column lists), and the backend validator (the runtime gate). A skill restating those rules would be a fourth copy that drifts the moment any of the three changes — and a drifted authoring guide silently teaches the wrong contract, the opposite of author-empowerment. So the body carries only a per-kind COLLECT checklist (what to gather, which is stable) and points at policy.md/schema.py for the rules, letting the validator be the single gate that rejects anything wrong. The disassembler test is held by requiring the address/ABI to come from `/research-disassembly`'s verified ladder (AP1/AP2/AP12 — never invented).

## Why the approval gate sits before the write, not before the skill (the user's fork 4 choice)

The user chose "agent runs up to the validated preview; user approves before any write." This matches AP18 verbatim — the maintainer approves the SPECIFIC entity BEFORE the row lands — and `design-authority` / `deferral-authority` (the user decides; the agent recommends and stops). The preview writes nothing, so an agent auto-invoking the skill and running it to the validated preview is harmless; the load-bearing gate is the one before `/confirm`. The rejected alternative (approve even to START) adds a second ask that guards a no-op (the preview) and either makes the user approve twice or approve blind before seeing the validated row. Putting the single gate before the write means the user always approves the EXACT validated row that will be committed.

## Why the test-plugin obligation is surfaced, not blocked (the user's fork 5 choice)

The user chose "surface it as a required follow-up." `policy.md` §"Test plugin requirement" says a new entity must land with a `test-plugins/cap-NN` row — but the skill's job is the DB row (via the backend); the test plugin is a code deliverable the backend path does not build. So the skill lands the row, then surfaces the owed test as the explicit follow-up to route to `/feature` / `/execute`, so it is never silently dropped (`deferral-authority` — the user decides when, the skill flags). The rejected hard-block alternative is stricter than policy.md itself (which is review-enforced + allows a documented backfill path) and would force code-authoring into a skill that doesn't build code, or block legitimately-staged work (the fact is verified, the row + test landing across a short sequence).

## Why a repo-local skill, not a system skill

The skill is wholly kcdx-specific: it drives the kcdx maintainer-tool backend, knows the nine kcdx address kinds, and enforces kcdx's AP18 / AP1 / AP12 + the cornerstones. It has no cross-repo meaning, so it lives in the repo's `.claude/skills/`, mirroring `/research-disassembly` (the only other repo-local skill). It carries no append-injection first line because, like `/research-disassembly`, it has no `.claude/repo/*.append.md` — every value it needs (the backend path, the kinds, the policy) is in-repo and named directly.

## Boundary with the sibling skills (no overlap)

- `/research-disassembly` VERIFIES the fact + produces provenance (its §6 hands off recording); this RECORDS the verified fact. Run research first; this consumes its output.
- The maintainer-tool GUI is the human authoring path (and owns the UPDATE jobs); this is the agent/programmatic ADD path. They drive the same backend.
- `/execute` / `/feature` author the owed test plugin this skill surfaces; this skill does not build code.
- `policy.md` + `schema.py` + the backend validator own the rules; this skill cites them and lets the validator gate — it restates none of them.
