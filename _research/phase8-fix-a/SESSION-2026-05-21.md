# Session 2026-05-21 — Stage 2 kickoff

## What we did

Set up the recon workspace under `_research/phase8-fix-a/` and built the
tooling for B+C harvest (string-anchor xref walks + call-graph from
known anchors). Validated the methodology against the lua_pcall anchor
and harvested 11 RVAs total — 9 of them on the LUA_API/LUALIB_API
surface kcdxLuaApi needs to resolve.

## Tools built

- `coff_inspect.py` — COFF .obj parser. Given `lapi.obj`, extracts every
  function symbol with its bytes and relocations. Lets us see what our
  compiled `lua_pcall` (etc.) calls so we can cross-reference against
  WHGame.dll's call sites.
- `callgraph_walk.py` — Capstone-based forward disassembly from an
  anchor RVA. Enumerates every direct CALL (`E8`) and tail JMP (`E9`)
  reachable on the hot path. Stops at RET or 4-CC pad.
- `string_xrefs.py` — Locates a string in `.rdata` and finds every
  code reference to it (LEA/MOV with rel32 operand). Uses `.pdata` /
  exception directory for authoritative enclosing-function bounds.

## Methodology validation

### PGO divergence (recorded in README)

Our compiled `lua_pcall` prologue diverges from WHGame's at byte +0x0A
(WHGame has `33 C0 (xor eax, eax)` ours doesn't). Confirmed approach A
(naive AOB) can't work alone for cross-build identification; B+C
methods are the load-bearing path. A remains useful as a weak check
for functions PGO didn't reshape.

### Productive xref strategy

Single string xref + .pdata-bounded function walk + source-level call
sequence matching gives 3-6 LUA_API identifications per anchor. The
"too many results to resume" string alone yielded 5 RVAs by walking
auxresume's call graph and matching against `lbaselib.c::auxresume`'s
source.

This is the workhorse pattern for the remaining 106 functions:
1. Pick a Lua stdlib function whose source we can read.
2. Find a unique error string it references.
3. Use `string_xrefs.py` to find it in WHGame.dll.
4. Walk the enclosing function with `callgraph_walk.py`.
5. Match call sites to source-level call sequence.

- `"bad argument #%d (%s)"` → `luaL_typerror`/`luaL_argerror` themselves (they ARE the API)

- `"attempt to %s a %s value"` → `luaG_typeerror`

Also: many luaopen_* routines (`luaopen_base`, `luaopen_string`, etc.)
build their library tables with `luaL_register` and a static `luaL_Reg[]`
— the `.rdata` table of `{"name", &lua_function}` pairs is a goldmine.
Find the `.rdata` table for, say, `luaopen_string`'s registration list
and every entry maps a known name to a known RVA. That's the highest
yield per unit effort and should be the next attack.
