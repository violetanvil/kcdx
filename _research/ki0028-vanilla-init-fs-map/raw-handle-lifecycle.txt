kcdx HANDLE (src/fs_takeover/file_handle.{h,cpp})
================================================================================
  KcdxHandle = (id<<1)|1, id = 1-based pool slot, smallest = 3. ODD tag (low bit=1).
  - kcdx OWNS every read/seek/tell/eof/close/getsize/mtime/cacheddata/find slot -> dispatches on the ODD TAG (low bit), NEVER the engine's handle-1<count test.
  - FILE* alignment (16-byte) -> low bits 0 -> kcdx odd handle never aliases the engine OS arm.
  - kcdx FOpen ALWAYS returns the odd handle for asset/non-asset/write alike (open_slots.cpp OpenResolvedAndMint).
  - kcdx does NOT call +0x268 (register), does NOT call +0x2c8 (post-open hook), does NOT touch the [this+0x40] pak vector, does NOT acquire [this+0x200] (uses its OWN g_poolLock leaf mutex).
  - kcdx AdjustFileName: loose hit -> disk path; PAK hit -> returns pName UNCHANGED; miss -> thunks original resolver (string-only).

DEVIATIONS (handle-lifecycle axis) ranked for the abort question
================================================================================
D1 (highest) — kcdx FOpen SKIPS the +0x268 register-handle slot and the +0x2c8 post-open hook that EVERY vanilla open fires.
   If the level-load path (or a teardown/validation it runs) later WALKS the engine's registered-open-handle structure (the thing +0x268 populates) and finds it EMPTY / inconsistent, a tested condition could flip.
   *** UNVERIFIED: the BODY of the +0x268 slot (what structure it writes, who reads it) was NOT read in any prior dump or this pass. This is the load-bearing un-bisected edge. ***
D2 — kcdx FOpen NEVER mints a pak-vector (index+1) handle; ALL kcdx handles are odd FILE*-class-range values. Vanilla mints index+1 for pak-resident files.
   Benign IF every handle consumer is kcdx-owned (it is, by design). A residual risk only if a NON-read-family vanilla consumer reads the handle as a [this+0x40] index — none found in priors (straddle falsified; FRead family owned).
D3 — kcdx uses its OWN g_poolLock, not the engine [this+0x200] pak-mgr SRW lock vanilla FOpen acquires. No shared-state coupling either way (kcdx pool is private), so low abort-relevance.
D4 — the pak-vector GROW side-effect (param_1[8]/[9] mutation, :240-256) never happens under kcdx. If anything downstream reads [this+0x40]/[this+0x48] as "count of open files", kcdx leaves it at the vanilla-seated value. Likely benign (read family is kcdx-owned) but UNVERIFIED whether the abort path reads that count.
