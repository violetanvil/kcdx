== THE LOAD-BEARING LINK FOR KI-0028 (slot-1 resolve gates the pak FILE open) ========
=====================================================================================
The archive factory (slot 72) STEP 1 runs the .pak path through AdjustFileName = CCryPak
vtable SLOT 1 (flag 0x10000) BEFORE STEP 3 opens the file. kcdx OWNS slot 1 on a full swap.
=> when the engine mounts a level component pak, the .pak path itself is resolved by kcdx's
   AdjustFileName/index-resolve. A kcdx miss/mis-normalize on a `data/levels/<lvl>/<c>.pak`
   path therefore reaches the MOUNT path, not only file-content serves.
   (front2 §"directory-index BUILD" step 1; fs-takeover-pak-mount-recon Q1 confirms slot1 read.)

== WHERE THIS REGION FEEDS THE LEVEL-LOAD ABORT =====================================
=====================================================================================
The abort tests "was the level's pak set / resource files found?" Two candidate mount-region
deviations could flip it, both routing through kcdx's slot-1 resolve (which kcdx owns):
  (a) the engine MOUNTS data/levels/<lvl>/*.pak at level-load -> the .pak path is slot-1
      resolved (factory STEP 1) -> a kcdx miss/mis-key on that .pak path fails the mount.
  (b) the engine reads level resource files (resourcelist.txt / component manifests) via
      FOpen (slot 36) -> slot-1 resolve -> kcdx miss -> the level's resource set is empty.
Both are kcdx-resolve gaps on the `levels/` vs `data/levels/` key, NOT a mount-mechanism fault.
The recursive index walk (asset_index.cpp recursive_directory_iterator) put the level paks'
CONTENTS in the index, yet the abort returned on a full swap — so the residual is a KEY/
NORMALIZATION coverage gap on what the level load requests, at the slot-1 resolve, not a
missing pak in the index. (apex: the deviation is in kcdx slot-1 resolve key-coverage for the
data/levels/ prefix, exercised via the mount-factory's slot-1 call AND/OR the resource-file FOpen.)
